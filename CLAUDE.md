# TraderEngine — Claude Code notes

## .NET solution / build
- Solution is `.slnx` (not `.sln`); use `dotnet sln <file>.slnx` / VS 2022 17.x+.
- Central Package Management is in effect: `Directory.Packages.props` (versions) + `Directory.Build.props` (shared properties: TargetFramework, Nullable, ImplicitUsings, RestorePackagesWithLockFile, and `IsTestProject`/`IsPackable` auto-set for any project named `*.Tests`).
- After changing `Directory.Packages.props` or any `.csproj`, regenerate lock files with `dotnet restore --force-evaluate`; verify with `dotnet restore --locked-mode`.
- Before assuming a `PackageReference` is redundant because a `ProjectReference`d project already has it, verify empirically (`dotnet restore` + `dotnet list package --include-transitive`) rather than reasoning from the reference graph alone — analyzer/source-generator packages (e.g. Riok.Mapperly) and anything under `PrivateAssets=all` never flow transitively, even without explicit blocking.
- Code style: explicit constructors, not C# primary constructors (verified: 13 vs 0 across the codebase) — don't apply IDE "use primary constructor" suggestions.

## Docker Compose / Visual Studio Container Tools
- `docker-compose.dcproj` (`Microsoft.Docker.Sdk`) can be added to `TraderEngine.slnx` safely — `dotnet build`/`test`/`restore` silently skip it (SDK only resolves inside VS), so it won't break CI or CLI-driven builds.
- VS Fast Mode debugging only builds a Dockerfile's *first* stage, then bind-mounts the host build output over it — a single-stage Dockerfile that `COPY`s a prebuilt `bin/Release/.../publish` folder will NOT work for one-click F5 (needs a manual `dotnet publish` first). Use a self-contained multi-stage Dockerfile (base/build/publish/final, SDK builds from source) for real one-click debugging; keep the prod/CI Dockerfile separate/untouched if CI depends on its current shape.
- The "host build output" Fast Mode bind-mounts into `/app` is the *entire live project source folder* (e.g. `D:\...\TraderEngine.Web` → `/app`), not a separately-produced `bin/Debug` copy — confirmed via `docker inspect <container> --format "{{json .Mounts}}"` while an F5 session was running. VS's Container Tools MSBuild targets (`Microsoft.VisualStudio.Azure.Containers.Tools.Targets`) also add their own dedicated `wwwroot` → `/app/wwwroot` mount automatically per web-project service, on top of that. This means edits to `wwwroot` (including compiled output from `pnpm run watch`) are visible inside a running Fast Mode container immediately, with zero extra `docker-compose.debug.yml` config needed — ASP.NET Core's `ReloadStaticAssetsAtRuntime` (default-enabled for non-published/dev "build manifest" runs, which Fast Mode always is) then re-serves the changed file with a recomputed ETag on the very next request, no rebuild or restart required (verified directly via native `dotnet run`: editing `wwwroot/js/site.js` while the process was running changed the served ETag/content-length/body on the next request). Don't manually add a redundant wwwroot bind mount to "fix" this — check `docker inspect --format "{{json .Mounts}}"` first, VS likely already did it. Also don't try to hand-simulate Fast Mode with a plain `bin/Debug` folder mount instead of the whole project source — that crashes the app outright at startup (`ArgumentException: The path must be absolute`), because a Windows-built static web assets manifest bakes in Windows absolute host paths (e.g. `D:\...\wwwroot\`) that are meaningless inside a Linux container; VS avoids this by mounting the live source tree itself rather than a copied build output.
- `--env-file` is a root-level Compose CLI flag only (`docker compose --env-file X up`, not `up --env-file X`) — can't be smuggled in via `DockerComposeUpArguments`/`DockerComposeBuildArguments` (those append after the subcommand).
- `DockerComposeEnvFilePath` (singular, documented) takes exactly one file. `DockerComposeEnvFilePaths` (plural, semicolon-delimited) is real and shipped but undocumented on Microsoft Learn — confirmed by decompiling `...MSBuild\Sdks\Microsoft.Docker.Sdk\tools\Microsoft.Docker*.dll` (`strings` + grep) and validating live via `MSBuild.exe docker-compose.dcproj -t:DockerGetComposeEnvFilePaths -getTargetResult:DockerGetComposeEnvFilePaths`. Use it to layer `.env.example;.env` (later file wins) instead of pre-merging files.
- A service's `env_file:` YAML key injects raw vars into the *container* and never participates in `${VAR}` interpolation when Compose parses the YAML — the two mechanisms don't interact, don't conflate them when `environment:` blocks rename/compose vars (e.g. `CMC_API_KEY` → `CoinMarketCap__API_KEY`).
- MSBuild.exe is at `C:\Program Files\Microsoft Visual Studio\18\Community\MSBuild\Current\Bin\amd64\MSBuild.exe`; in Git Bash use `-t:Target` not `/t:Target` (the `/` gets mangled into a path).
- VS live-syncs `.slnx`/`.dcproj`/`Directory.Packages.props`/`.csproj` while open in the IDE — expect concurrent external edits mid-session; re-read a file before editing it rather than assuming your last-known copy is current.
- Compose merges (unions) a service's `profiles` list across `-f` files by default — `profiles: []` in an overlay does NOT clear a base file's `profiles: [foo]`, it stays `[foo]`. Force a real override with the `!reset` YAML merge tag (`profiles: !reset []`). Verified via `docker compose config --services`.
- `composeLaunchUrl`'s `{ServiceIPAddress}`/`{ServicePort}` tokens require VS to resolve and directly reach the container's internal Docker-network IP — a separate, less reliable path than the host-published port already confirmed working (`docker-compose.yml`'s `traderengine.web` maps `8081:80`). When the browser silently never launches on F5 despite debugging working fine (raising `launchBrowserTimeout` doesn't help either), that token resolution/reachability is the likely failure point. Even a partial fix (`"{Scheme}://localhost:8081"`, token + literal host mixed) fails outright with "Container Tools" Output pane error `The URL '...' is not valid.` — mixing tokens and literals isn't tolerated. Use a fully literal URL instead (`"http://localhost:8081"`, no tokens at all); this app has no SSL configured anywhere so hardcoding the scheme is safe. Keep the literal port in sync with `docker-compose.yml`'s `ports:` mapping if it ever changes.
- `launchSettings.json`'s `launchBrowserTimeout` (Docker Compose only, seconds) defaults far too low for this app — Microsoft's own docs example uses `1`. `traderengine.web` runs an EF Core migration (`Database.MigrateAsync`) plus admin-seed logic before Kestrel starts listening, which blows past that window; VS then silently skips the browser launch (no error) rather than failing loudly. Set it explicitly (e.g. `60`) in the `"Docker Compose"` launch profile. Plain JSON, not JSONC — no comments allowed in this file.
- VS's "Docker Compose" F5 debugging does not pass `--profile <name>` even when `launchSettings.json`'s `composeProfile.includes` names one, AND expects a running container for *every* service defined across whatever files it loads (base `docker-compose.yml` + `AdditionalComposeFilePaths`), regardless of that service's `profiles:` gate — a profile-gated service in those files is silently skipped by `docker compose up`, then VS fails with "Can not find the container for the service '\<name\>'." Confirmed by reproducing manually (`docker compose up` with no `--profile` flag skips the same services). Two different fixes depending on intent: if the service *should* always run under F5, clear its `profiles` in the VS-only debug overlay with the `!reset` tag (see above); if it must stay opt-in-only (e.g. a one-shot job container), keep it out of every file the dcproj loads entirely — put it in its own compose file, referenced only manually via `-f`, never added to `AdditionalComposeFilePaths` or the base file. The `launchSettings.json` `composeProfile.includes` key was removed as dead/misleading rather than trusted, once this was understood.

## PowerShell 5.1 (this machine's default)
- `Set-Content -Encoding utf8NoBOM` doesn't exist (PS 6+ only). Use `[System.IO.File]::WriteAllLines($path, $lines, (New-Object System.Text.UTF8Encoding $false))` instead.
- `Get-Content` without `-Encoding UTF8` reads via the system codepage, mangling non-ASCII characters (e.g. em dashes become `â€”`) — always pass `-Encoding UTF8` explicitly when round-tripping repo files.
